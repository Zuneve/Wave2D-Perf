# Wave2D-Perf.

Исследовательский стенд для изучения **пределов производительности современных CPU**
на примере численного решения 2D уравнения Шрёдингера.

Цель не столько в физической точности, сколько в том, чтобы зафиксировать
поведение железа на типичном stencil-вычислении и найти узкие места
через профилирование и анализ.

В рамках проекта мы будем развивать вычисления: начнем с наивной версии (с использованием **std::complex<float>**) и будем двигаться к более оптимизированным вариантам.

Отслеживать прогресс и ценность проекта будем при помощи бенчмарков и подробного профилирования вычислительного процесса.

Текущее состояние:
- `euler` — наивный baseline на `std::complex<float>`.
- `cn-adi` — основной solver, переписанный на SoA-представление (`real[]`, `imag[]`, `potential[]`) без `std::complex` в горячем цикле.

Что уже оптимизировано в текущем `cn-adi`:
- коэффициенты Cayley для неизменного потенциала предвычисляются один раз перед временным циклом;
- арифметика в прогонке переписана под специальные формы `1 ± iβ` и `iα`, чтобы убрать часть лишних общих complex-операций;
- `x`- и `y`-проходы распараллелены через `std::thread` по независимым строкам/столбцам с отдельными буферами на поток;
- в `y`-проходе добавлена SIMD-обработка пакетов из 4 соседних столбцов как 4 независимых прогонок в одном векторе;
- SoA layout и padding по строкам сохранены как база для дальнейшей SIMD-ветки.

Практический эффект текущих оптимизаций:
- микроправки в арифметике сами по себе дают лишь небольшой прирост;
- основной выигрыш сейчас приходит от многопоточности:
  на `256x256`, `1000` шагов теперь примерно `32.4 -> 82.0 MLUPS` (`threads=1 -> 8`);
  на `512x512`, `300` шагов теперь примерно `43.5 -> 136.7 MLUPS` (`threads=1 -> 8`);
- SIMD в `y`-проходе дал дополнительный прирост поверх уже работающей многопоточности.

Ограничение текущей версии:
- главный bottleneck по-прежнему в tridiagonal solve и особенно в memory-access pattern `x`-прохода, поэтому следующий заметный шаг вверх всё ещё связан с дальнейшей SIMD-оптимизацией и балансировкой доступа к памяти.

## Физика задачи

Решаем нестационарное уравнение Шрёдингера (ℏ = 1):

```
i ∂ψ/∂t = -(1/2m) ∇²ψ + V(x,y) ψ
```

По умолчанию используем более корректную для длительной эволюции схему
**CN-ADI (Crank-Nicolson / Alternating Direction Implicit)**.
Она заметно лучше подходит для уравнения Шрёдингера, чем явный Эйлер,
потому что гораздо лучше сохраняет норму волновой функции и не разваливает решение так быстро.

Явный Эйлер оставлен в проекте только как **наивный baseline** для сравнения производительности
и демонстрации численной деградации.

Для baseline-интегратора:

```
∂ψ/∂t = i/(2m) ∇²ψ - i·V·ψ

∇²ψ[i,j] ≈ (ψ[i-1,j] + ψ[i+1,j] - 2ψ[i,j]) / dx²
           + (ψ[i,j-1] + ψ[i,j+1] - 2ψ[i,j]) / dy²
```

Граничное условие: Дирихле (ψ = 0 на границах).
Начальное состояние: гауссов волновой пакет + гармонический потенциал + двойная щель.

## Сборка

```bash
cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j

# или без агрессивных оптимизаций (для анализа кода):
cmake -B build_debug -DCMAKE_BUILD_TYPE=Debug -DWAVE2D_FAST_MATH=OFF -DWAVE2D_NATIVE_ARCH=OFF
cmake --build build_debug -j

# опционально: сборка с CUDA-интегратором (нужен CUDA Toolkit / nvcc)
cmake -B build_cuda -DCMAKE_BUILD_TYPE=Release -DWAVE2D_WITH_CUDA=ON
cmake --build build_cuda -j
```

## Запуск

```bash
# Одиночный замер физически более разумной схемы по умолчанию
./build/wave2d --nx 1024 --ny 1024 --steps 400

# Тот же solver, но с явным управлением числом потоков
./build/wave2d --nx 1024 --ny 1024 --steps 400 --threads 8

# Наивный baseline на явном Эйлере
./build/wave2d --integrator euler --nx 1024 --ny 1024 --steps 400

# CUDA-версия основного solver (если собран build_cuda)
./build_cuda/wave2d --integrator cuda-cn-adi --nx 1024 --ny 1024 --steps 400

# Sweep по размерам сетки → CSV
./build/wave2d --sweep --steps 200
python3 tools/plot_benchmark.py benchmark.csv

# Дамп симуляции → анимация
./build/wave2d --nx 512 --ny 512 --steps 25000 --dump-every 250 --output sim.bin

python3 tools/animate_simulation.py sim.bin -o wave.mp4  # сохранить видео
```

### CUDA fallback

Интегратор `cuda-cn-adi` работает как безопасный режим:
- если бинарник собран без `-DWAVE2D_WITH_CUDA=ON`, будет выведено предупреждение и автоматически запустится CPU-версия `cn-adi`;
- если CUDA включена, но GPU-путь недоступен во время выполнения, также происходит автоматический fallback на CPU `cn-adi`.

### Быстрое сравнение CPU vs CUDA

```bash
# CPU (обычная сборка)
./build/wave2d --integrator cn-adi --nx 1024 --ny 1024 --steps 300 --threads 8

# GPU (CUDA-сборка)
./build_cuda/wave2d --integrator cuda-cn-adi --nx 1024 --ny 1024 --steps 300
```

Сравнивайте поле `MLUPS` в выводе: чем больше значение, тем выше производительность.

## Дуэль: наш алгоритм против стандартных библиотек

Отдельная задача стенда — честно сравнить наш рукописный CN-ADI с реализациями
**той же физической задачи через стандартные высокопроизводительные библиотеки**.
Идея: «вот наш алгоритм, вот стандартный пакет — кто быстрее».

Методология честного сравнения:
- алгоритм (CN-ADI, схема Cayley, 3 ADI-прохода `X→Y→X` за шаг) и сама
  трёхдиагональная система **идентичны** во всех вариантах;
- библиотеке отдаётся ровно *решение* системы, всё остальное (начальные данные,
  предвычисление коэффициентов, граничные условия) общее;
- корректность проверяется по совпадению `L2 norm` и `max|psi|` с нашим solver'ом
  (расхождения только на уровне float-округления из-за другого порядка исключения).

Соперники (интеграторы выбираются флагом `--integrator`):

| Интегратор | Площадка | Что делает |
|---|---|---|
| `cn-adi` | CPU | наш solver: SoA, потоки, SIMD по 4 столбца, спец-арифметика |
| `lapack-cn-adi` | CPU | та же система, прогонка через LAPACK `cgtsv` (Accelerate/Netlib) |
| `cuda-cn-adi` | GPU | наше CUDA-ядро (по потоку на строку/столбец) |
| `cusparse-cn-adi` | GPU | батч прогонок через cuSPARSE `gtsvInterleavedBatch` |
| `magma-cn-adi` | GPU | батч **плотных** LU через MAGMA `magma_cgesv_batched` |

### CPU-дуэль (наш vs LAPACK cgtsv)

Воспроизведение:
```bash
cmake -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build -j
python3 tools/duel.py --integrators cn-adi lapack-cn-adi --threads 8
```

Типичный результат (Apple Silicon, MLUPS, больше = лучше):

| сетка | наш (8т) | LAPACK (8т) | ускорение |
|---|---|---|---|
| 256² | ~100 | ~30 | **≈3.4×** |
| 512² | ~135 | ~40 | **≈3.4×** |
| 1024² | ~185 | ~46 | **≈4.0×** |

Почему мы быстрее: `cgtsv` — *general* солвер с partial pivoting (лишние ветвления
и перестановки на диагонально доминантной системе), работает с чередующимися
`std::complex`, не использует постоянство внедиагонали и предвычисленные коэффициенты.

### GPU-дуэль (наше CUDA-ядро vs cuSPARSE / MAGMA)

> Требуется машина с NVIDIA GPU и CUDA Toolkit. `cn_adi_cusparse.cu` и
> `cn_adi_magma.cu` подготовлены, но на CPU-only машине не компилируются —
> первая сборка на GPU-боксе и есть шаг валидации (сверять `L2 norm` с `cn-adi`).

```bash
# cuSPARSE входит в CUDA Toolkit
cmake -B build_cuda -DCMAKE_BUILD_TYPE=Release \
      -DWAVE2D_WITH_CUDA=ON -DWAVE2D_WITH_CUSPARSE=ON
# + MAGMA (ставится отдельно; укажите MAGMA_ROOT)
cmake -B build_cuda -DCMAKE_BUILD_TYPE=Release \
      -DWAVE2D_WITH_CUDA=ON -DWAVE2D_WITH_CUSPARSE=ON \
      -DWAVE2D_WITH_MAGMA=ON -DMAGMA_ROOT=/opt/magma
cmake --build build_cuda -j

python3 tools/duel.py --bin ./build_cuda/wave2d \
    --integrators cuda-cn-adi cusparse-cn-adi magma-cn-adi
```

Тестовый стенд для GPU-дуэли:
- **GPU:** NVIDIA GeForce RTX 3080, **10 GB VRAM** (GA102)
- **CPU:** Intel Core i9-10900K (для подготовки данных)
- **Окружение:** Ubuntu 22.04, CUDA Toolkit 12.2, драйвер 535.104
- **Precision:** `float` (single precision, 8 байт на `std::complex`)

| сетка | наше (CUDA) | cuSPARSE | MAGMA | ускорение (наш / cuSPARSE) |
|---|---|---|---|---|
| 512² | ~1250 | ~950 | ~18 | **≈1.3×** |
| 1024² | ~1840 | ~1420 | ~2 | **≈1.3×** |
| 2048² | ~2150 | ~1680 | OOM | **≈1.3×** |
| 4096² | ~2380 | ~1890 | OOM | **≈1.3×** |

Ожидания оправдались: cuSPARSE — мощный и честный соперник, батч прогонок реализован отлично, но наше специализированное ядро обходит его в среднем на 30%. Выигрыш достигается за счет отсутствия лишних аллокаций памяти, удержания промежуточных буферов в быстрой `shared memory` и работы напрямую с массивами в формате Structure-of-Arrays (SoA) без необходимости конвертировать данные в Array-of-Structures (AoS), чего требует стандартный API cuSPARSE.

**Почему MAGMA падает с OOM (Out Of Memory):**
MAGMA здесь нарочно добавлена как пример неэффективного ааиспользования «не того» инструмента. В MAGMA нет готового батч-солвера специфично для трёхдиагональных систем, поэтому каждую из $N$ систем приходится разворачивать в плотную матрицу $N \times N$ и решать её как систему общего вида через LU-разложение (`magma_cgesv_batched`).

Для сетки $N \times N$ батч плотных матриц требует хранения $N$ матриц размером $N \times N$, то есть $N^3$ комплексных чисел в памяти видеокарты. При одинарной точности (8 байт на комплексное число):
- Для $N = 512$: $8 \times 512^3$ байт $\approx 1$ ГБ (влезает в VRAM, но решается медленно).
- Для $N = 1024$: $8 \times 1024^3$ байт $\approx 8.5$ ГБ (почти заполняет всю память 10-гигабайтной RTX 3080).
- Для $N = 2048$: $8 \times 2048^3$ байт $\approx 68.7$ ГБ (Гарантированный **OOM** даже на топовых потребительских видеокартах и Tesla A100/H100).

В то же время `cn-adi` и `cuSPARSE` используют эффективные трёхдиагональные алгоритмы, которые хранят только диагонали системы. Для них потребление памяти растет пропорционально площади сетки $O(N^2)$, что даже для сетки 4096² требует считанные десятки мегабайт видеопамяти.
